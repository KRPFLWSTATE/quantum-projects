1. DONE with a finished timestamp did not establish final billing. The usage interpreter could turn pending IBM billing into a final zero charge. IBM explicitly documents that usage() returns zero while billing is pending:
https://quantum.cloud.ibm.com/docs/en/api/qiskit-ibm-runtime/runtime-job-v2#usage
The repair requires explicit completed billing metadata for a zero charge, retains unknown/pending reservations, and rejects invalid numeric charges.

2. Default resume could construct FakeRuntimeJob when raw data already existed, potentially importing its synthetic 2.0-second charge into accounting. Default resume also returned before binding a provider when the job ID was absent. The repair retrieves the real provider by ID or tags, never substitutes mock usage, and allows offline receipt recovery only with a previously resolved archived charge. Resume reports zero new submissions and accounting remains idempotent. Failed terminal jobs are archived and charged once; unresolved transport errors retain their reservations.

3. Dispatch emitted an immediate timeout through placeholder actor functions. The repair waits for the actual 30-second deadline, persists verified incumbent fallbacks for P1-P3 while the provider worker waits, and prevents late results from replacing those final decisions. P0 remains the unguarded ablation. Result receipt and dispatch timestamps survive interruption; unknown timing is not replaced with a fictitious zero elapsed time. This is a deterministic controller experiment, not proof of autonomous AI or organisation-wide deployment. Specification changes and 5/30/300-second sensitivity schedules remain explicitly identified replay analyses.

4. Decoded results are persisted before querying usage. Policy rows carry fixture, depth, PUB and request identifiers. Resume refreshes the archive analysis and return packet using the same reporting commands as normal completion.
